# Claude 스킬 작성 규칙 7가지

유튜브 영상 「앤트로픽 피셜: 클로드 스킬 만드는 규칙 바뀜 (공식 7가지)」(낭만빌더 김스듴, 2026-10-31, 11분 54초)을 정리했다. 영상은 Anthropic이 고친 스킬 작성 모범 사례를 설명한다. 이 페이지는 영상의 자막과 YouTube 요약을 근거로 하며, Anthropic 공식 문서를 직접 확인하지는 않았다.

영상의 결론: 스킬 실력은 문장을 잘 쓰는 것보다 **파일을 어떻게 놓고 어떤 검사를 돌리느냐**로 갈린다.

## 배경: 긴 참고 파일은 앞부분만 읽힌다

Claude는 스킬 안의 긴 참고 파일을 열 때 끝까지 읽지 않고 앞 100줄 정도만(`head`) 보고 지금 필요한 파일인지 판단할 때가 많다. 그래서 100번째 줄 아래에 쓴 중요한 규칙은 없는 것과 같다. 아래 규칙 중 1·4번이 이 문제를 다룬다. (영상 0:00)

## 1. 100줄 넘는 참고 파일은 맨 위에 목차를 단다 (0:48)

목차가 있어야 Claude가 전체를 읽을지, 필요한 부분으로 바로 갈지 고를 수 있다. 예) API 설명서 맨 위에 "인증과 설정 / 핵심 기능 / 고급 기능 / 오류 처리 / 코드 예시" 다섯 줄.

적용: "스킬 폴더의 스킬을 다 훑어서 100줄 넘는 참고 파일을 찾고, 제목에 맞춰 맨 위에 목차를 넣어 줘."라고 시키면 된다.

## 2. 일의 성격에 맞춰 자유도를 정한다 (1:33)

얼마나 자세히 쓸지는 그 일이 **얼마나 쉽게 깨지고 얼마나 매번 달라지는지**로 정한다.

| 자유도 | 형태 | 예 |
| --- | --- | --- |
| 높음 | 목표만 주는 글 지시 | 코드 리뷰, 영업 통화 돌아보기, 글 초안 |
| 중간 | 설정값이 있는 템플릿 | 매주 보내는 고객 보고서(차트 유무, 형식) |
| 낮음 | 정해진 스크립트를 그대로 실행 | DB 이전, 청구서 발행, 환불, 회원 삭제 |

- 한 스킬 안에서도 **단계마다** 자유도를 다르게 줄 수 있다. 예) 안내문 쓰기는 풀고 청구서 만들기는 잠근다.
- 단계마다 "Claude가 이걸 다르게 하면 무슨 일이 생기지?"를 묻는다. 별일 없으면 풀고, 큰일 나면 잠근다.
- 잠근다는 것은 보통 글을 더 쓰는 것이 아니라 **스크립트로 바꾸는 것**이다.

## 3. 쓸 모델로 각각 테스트하고 머릿말에 적는다 (3:56)

스킬 결과는 밑에 깔린 모델에 따라 달라진다.

- 예전 모델은 단계를 자주 건너뛰어 번호와 대문자 강조가 필요했다. 최신 모델은 반대로, 예전 모델용으로 쓴 깐깐한 지시가 결과를 망칠 수 있다. 지시를 뺐을 때 더 잘하면 그 지시는 지운다.
- 모델마다 점검 질문이 다르다: Haiku는 안내가 충분한가? Sonnet은 군더더기 없이 명확한가? Opus는 설명이 너무 많지 않은가?
- 같은 일을 Haiku·Sonnet·Opus로 한 번씩 돌린다. Haiku가 단계를 빼먹으면 그 단계를 더 분명히 쓰거나 스크립트로 잠근다. Opus가 스킬이 있을 때 더 못하면 지시를 하나씩 지운다.
- 남에게 나눠 줄 스킬은 맨 위 머릿말에 **어떤 모델용인지** 적는다.

## 4. 참조는 한 단계만 둔다 (5:47)

- SKILL.md 본문은 500줄 안으로 두고 나머지의 목차처럼 쓴다. 긴 내용은 파일로 뺀다.
- 여러 분야를 다루는 스킬은 참고 파일을 분야별로 나눈다(예: 데이터 스킬의 재무·영업·제품·마케팅 파일). 필요 없는 파일은 아예 열리지 않는다.
- 스크립트는 실행만 되고 읽히지 않으므로 컨텍스트를 쓰지 않는다.
- SKILL.md → A → B처럼 겹겹이 참조하면 사슬 끝의 B는 앞부분만 읽힐 가능성이 크다. **모든 참고 파일을 SKILL.md에서 바로 연결**한다.

적용: SKILL.md가 가리키는 파일을 적어 보고, 다른 파일을 거쳐야만 닿는 파일이 있으면 SKILL.md에서 바로 잇는다.

## 5. 긴 작업에는 체크리스트를 준다 (7:52)

- 복잡한 일은 단계로 쪼개고 체크리스트를 준다. Claude가 답변에 복사해 두고 하나씩 체크하며 간다.
- 순서가 중요할 때만 쓴다(보고서 전에 데이터 확인 등). 순서가 상관없으면 뺀다.
- 체크리스트도 목표만 주고 방법은 열어 둘 수 있다. 예) 연구 정리 5단계: 자료 다 읽기 → 핵심 주제 찾기 → … → 인용 확인.
- "모든 주장에 출처가 있는지 보고, 빠졌으면 3단계로 돌아가라" 같은 **되돌아가기 한 줄**이 있으면 실패한 단계를 체크하고 넘어가지 않는다.

## 6. 스스로 검사하고 고치는 루프를 넣는다 (8:59)

- 검사를 돌리고 → 틀린 것을 고치고 → 통과할 때까지 반복한다. 검사가 꼭 코드일 필요는 없다(예: 초안을 스타일 가이드·브랜드 말투 문서와 비교).
- 초안이 가이드에 아직 없는 이유로 걸리면, 작업 끝에 Claude에게 새 규칙을 제안하게 하고 사람이 승인하면 문서에 넣는다. 다음부터 그 규칙으로도 검사하므로 스킬이 스스로 좋아진다.

## 7. 필요한 설치 명령을 스킬 안에 적는다 (9:47)

- 직접 만든 스킬은 내 컴퓨터에서는 돌아가지만, 팀원 컴퓨터나 새 세션에는 필요한 도구가 없어 첫날 고장 나기 쉽다.
- 도구가 깔려 있다고 가정하지 않는다. "PDF 라이브러리로 처리해라" 대신 "필요한 패키지(이름 명시)를 설치해라"로 쓴다. 이미 깔려 있으면 Claude가 그 단계를 건너뛴다.
- 스크립트마다 설치 방법을 옆에 붙인다.

## 점검 목록

- [ ] 100줄 넘는 참고 파일에 목차가 있다
- [ ] 단계마다 자유도(글 / 템플릿 / 스크립트)를 정했다
- [ ] 쓸 모델로 각각 테스트했고, 머릿말에 대상 모델을 적었다
- [ ] 모든 참고 파일이 SKILL.md에서 한 단계로 연결된다
- [ ] 순서가 중요한 긴 작업에 체크리스트와 되돌아가기 줄이 있다
- [ ] 검사 → 수정 → 반복 루프가 있다
- [ ] 필요한 패키지와 설치 명령이 적혀 있다
