# DECISIONS — wiki-docs v0.1

## D-1. 위키 페이지는 wiki/ 아래 분야별 폴더에 두고, 분야 폴더는 필요할 때 추가한다

**선택**

위키는 `wiki/` 하나다. 페이지는 분야별 폴더에 둔다. 분야 폴더는 미리 만들지 않고, 그 분야의 첫 페이지를 저장할 때 사람에게 분야를 확인받아 만든다. 여러 분야에 걸치는 내용은 한 분야에 두고 다른 분야에서 링크로 잇는다.

**근거**

사용자 답 "분야별 폴더", 사용자 지시 "분야는 아직 정해지지 않아서, 미리 만들지 않습니다. 필요한 경우 추가하는 것으로 하겠습니다." 루트 INTENT "위키는 하나다. 분야는 위키 안에서 나눈다." 분야 확인은 AGENTS "모르면 지어내지 말고 묻는다"에서 왔다.

**배제한 대안**

- **평평한 폴더 + 태그** — 사용자가 분야별 폴더를 골랐다. 배제.
- **분야 폴더 미리 만들기** — 분야가 정해지지 않았다. 배제.

---

## D-2. wiki/ 이름은 영문 소문자·숫자·하이픈으로 짓고, raw/는 폴더만 영어로 하고 파일 이름은 원래대로 둔다

**선택**

`wiki/` 아래 폴더·파일 이름은 `[a-z0-9-]`와 확장자만 쓴다. 한글 제목은 frontmatter `title`과 본문 제목에 쓴다. `raw/` 아래 폴더 이름은 영어로 짓고, 파일 이름은 한국어·영어 모두 쓸 수 있으며 원래 이름을 바꾸지 않는다.

**근거**

사용자 답 "영문 소문자 + 하이픈"(wiki/), "폴더 이름은 영어이고, 파일명은 한국어/영어 일수 있습니다."(raw/). raw/ 파일 이름을 바꾸지 않는 것은 D-3 "원본은 고치지 않는다"와 맞는다.

**배제한 대안**

- **wiki/ 한글 이름** — URL·링크에서 인코딩된다. 사용자가 고르지 않았다. 배제.
- **raw/도 영문 소문자-하이픈으로 바꾸기** — 원본 폴더 안 문서끼리의 상대 링크가 깨질 수 있다. 사용자가 고르지 않았다. 배제.

---

## D-3. inbox/ 원본은 사람이 넣거나 사람의 요청으로 에이전트가 넣고, 정리 후 raw/<분야>/에 고치지 않고 보관한다

**선택**

원본은 `inbox/`에 들어온다. 사람이 데스크탑·노트북에서 넣거나 GitHub 웹에서 바로 올릴 수 있고, 사람이 요청하면 에이전트가 넣을 수도 있다. 원본은 두 가지다.

- 마크다운 문서를 담은 폴더.
- 유튜브 영상의 자막·요약 텍스트(D-15).

에이전트가 위키 페이지로 정리한 뒤 원본을 폴더 구조 그대로 `raw/<분야>/`로 옮기고, 그 뒤로는 고치지 않는다. 분야를 정할 수 없는 원본은 옮기지 않고 사람에게 묻는다.

**근거**

사용자 답 "inbox → raw 보관", "분야별". GitHub 웹 업로드는 루트 INTENT에서 버전 문서로 옮기기로 한 사용자 답("버전 문서로 옮기기")이다. 넣는 주체와 원본 종류는 사용자 지시 "inbox에는 사람이 추가할 수도/사람의 요청으로 에이전트가 추가할 수도 있습니다. 1. 마크다운 문서를 포함한 폴더 2. 유튜브 링크에 대한 동영상 내용 전체 또는 요약본"이다.

**배제한 대안**

- **정리 후 원본 삭제** — 원본이 git 이력에만 남는다. 사용자가 고르지 않았다. 배제.
- **raw/ 날짜별·단일 폴더** — 사용자가 분야별을 골랐다. 배제.

---

## D-4. 외부 검색으로 가져온 자료는 출처 URL만 남기고 raw/에 저장하지 않는다

**선택**

외부 검색 내용을 위키에 정리할 때는 페이지 frontmatter `sources`에 URL과 확인한 날짜를 적는다. `raw/`에는 사람이 넣은 원본만 둔다.

**근거**

사용자 답 "출처 URL만 남기기". 루트 INTENT "원본 자료는 사람이 넣거나 에이전트가 외부 검색으로 가져오며, 위키 페이지는 에이전트가 출처를 밝혀 정리한다."

**배제한 대안**

- **raw/에 발췌도 저장** — 링크가 사라져도 근거가 남지만 파일이 많아진다. 사용자가 고르지 않았다. 배제.

---

## D-5. 페이지 frontmatter는 title·sources·updated·tags·status 다섯 항목이고, 새 페이지는 draft다

**선택**

`index.md`를 뺀 모든 위키 페이지는 YAML frontmatter에 `title`, `sources`, `updated`(`YYYY-MM-DD`), `tags`, `status`(`draft`·`stable`)를 둔다. 새 페이지는 `draft`로 만들고, `stable`로는 사용자가 지시할 때만 바꾼다.

**근거**

사용자 답 "최소 + 태그·상태", "WIKI.md, 새 페이지는 draft".

**배제한 대안**

- **최소 세 항목(title·sources·updated)** — 사용자가 태그·상태를 더했다. 배제.
- **frontmatter 없음** — 사용자가 고르지 않았다. 배제.

---

## D-6. 링크는 표준 마크다운 상대 링크로 쓴다

**선택**

`[텍스트](상대경로.md)` 형식만 쓴다. `[[위키링크]]`는 쓰지 않는다.

**근거**

사용자 답 "표준 마크다운 링크". GitHub 웹에서 바로 링크로 동작한다.

**배제한 대안**

- **위키링크 `[[…]]`** — GitHub 웹에서 링크로 동작하지 않는다. 배제.

---

## D-7. 최상위 wiki/index.md와 분야별 index.md 두 단계로 목차를 둔다

**선택**

`wiki/index.md`는 분야 목록을, 분야 `index.md`는 그 분야 페이지를 한 줄씩 링크한다. 페이지를 추가·삭제·이름변경할 때 해당 `index.md`를 같이 고치고, 분야를 추가할 때 `wiki/index.md`도 고친다.

**근거**

사용자 답 "분야별 index.md + 최상위 index.md".

**배제한 대안**

- **최상위 index.md 하나** — 사용자가 고르지 않았다. 배제.
- **목차 없음** — 사용자가 고르지 않았다. 배제.

---

## D-8. 수식은 LaTeX($…$, $$…$$)로 쓴다

**선택**

인라인은 `$…$`, 블록은 `$$…$$`로 쓴다.

**근거**

사용자 답 "$…$ / $$…$$ LaTeX". GitHub와 대부분의 마크다운 편집기에서 렌더링된다.

**배제한 대안**

- **수식 규칙 없음** — 사용자가 고르지 않았다. 배제.

---

## D-9. 위키 검색은 index.md를 먼저 보고, 못 찾으면 wiki/ 본문을 키워드로 검색한다

**선택**

질문을 받으면 `wiki/index.md`와 분야 `index.md`에서 관련 페이지를 찾는다. 못 찾으면 `wiki/` 전체를 키워드로 검색(grep)한다. 별도 검색 도구는 두지 않는다.

**근거**

사용자 답 "index → 본문 검색". 루트 INTENT "질문에는 위키를 먼저 찾고, 외부 검색은 그다음이다."

**배제한 대안**

- **본문 검색만** — 사용자가 고르지 않았다. 배제.

---

## D-10. 답은 위키 내용과 외부 검색 내용을 출처를 나눠 보여 주고, 위키 저장은 확인받은 뒤에만 한다

**선택**

위키에서 찾은 부분은 페이지 경로를, 외부 검색 부분은 URL을 붙여 나눠 보여 준다. 위키에 없거나 사용자가 더 자세히 요청하면 외부 검색을 한다. 외부 검색을 했으면 답 끝에 "위키에 추가할까요?"를 묻고, 사용자가 예라고 하거나 먼저 추가를 지시했을 때만 저장한다.

**근거**

사용자 답 "출처를 나눠 표시", "물어본 뒤 저장". 사용자가 알려 준 사용 방법 "wiki를 먼저 찾아서… 없으면 웹 또는 외부 검색", "상세 내용을 요청하면 wiki에 없는 내용을 추가 외부 검색", "사용자에게 wiki에 추가할 것을 문의 또는 사용자가 위키에 추가 지시". 루트 INTENT "위키에 추가하는 것은 사용자가 확인하거나 지시한 내용뿐이다."

**배제한 대안**

- **합쳐서 답** — 사용자가 고르지 않았다. 배제.
- **항상 자동 저장** — 사용자가 "물어본 뒤 저장"을 골랐다. 배제.

---

## D-11. 기존 페이지와 겹치면 없던 내용만 보태고, 내용이 다르면 고치기 전에 묻는다

**선택**

새로 조사한 내용 중 기존 페이지에 없던 것은 그 페이지에 보태고 `sources`·`updated`를 고친다. 기존 내용과 다르면 고치기 전에 두 내용을 보여 주고 사용자에게 묻는다.

**근거**

사용자 답 "보태기, 다르면 묻기". 루트 INTENT "새로 조사한 내용은 위키에 정리해 쌓는다."

**배제한 대안**

- **항상 새 페이지** — 같은 주제가 여러 페이지로 흩어진다. 사용자가 고르지 않았다. 배제.

## D-12. 위키 작업 지침은 루트 WIKI.md에 두고, AGENTS.md에서 한 줄로 가리킨다

**선택**

질문 → 검색 → 저장 흐름, 원본 정리, 페이지 양식 같은 작업 지침을 루트 `WIKI.md`에 쓴다. `AGENTS.md`에 "위키 작업은 WIKI.md를 따른다"는 한 줄을 넣는다.

**근거**

사용자 답 "별도 문서 + AGENTS.md에서 가리킴", "WIKI.md". AGENTS.md는 claude·codex·agy가 모두 읽는다.

**배제한 대안**

- **AGENTS.md에 직접** — AGENTS.md가 길어진다. 사용자가 고르지 않았다. 배제.
- **Claude 스킬** — Claude Code에서만 동작한다. 사용자가 고르지 않았다. 배제.

**선택**

사용자 답 "사람이 요청할 때". 버전 INTENT 제외 범위 "자동 실행"과도 맞는다.

**배제한 대안**

- **세션 시작 때마다** — 사용자가 고르지 않았다. 배제.

## D-14. 작업 시작 때 pull하고 끝날 때 commit하며, push는 사람에게 확인받는다

**선택**

에이전트는 작업 전에 `git pull`, 작업 후 커밋한다. `push`는 매번 사람에게 확인받은 뒤 한다.

**근거**

사용자 답 "시작 시 pull, 끝날 때 commit·push". 루트 INTENT "문서 작업은 주로 데스크탑 또는 노트북에서 한다."

**배제한 대안**

- **커밋까지만** — 사용자가 고르지 않았다. 배제.

## D-15. 유튜브는 요청할 때 자막·요약·둘 다 중에서 고르고, 자막은 youtube-kit으로, 요약은 ego-lite로 가져온다

**선택**

사람이 유튜브 링크를 주며 요청하면, 무엇을 받을지(자막 전체 / YouTube 요약 / 둘 다)를 그때 사람이 고른다. 자막은 `C:\winpython\WPy64-31180_cpu` 환경에 설치된 youtube-kit(`D:\projects\youtube-kit`, yt-dlp 기반)으로 받는다. 트랙은 1순위 원본 언어, 2순위 한국어 번역으로 고른다(2026-11-01 사용자 지시로 추가). 수동 자막이 있으면 같은 언어의 자동 자막보다 먼저다. 두 순위의 트랙이 모두 없으면 `youtube-kit info`로 트랙 목록을 보여 주고 사람에게 묻는다. 요약은 ego-lite 브라우저에서 YouTube 자체 요약 기능(프리미엄 회원 기능)으로 가져온다. 영상·음성 파일은 받지 않는다.

**근거**

사용자 답 "요청할 때 고름", "넣기", "유튜브 자막은 1순위 원본 언어 2순위 한국어 번역". 사용자 지시 "yt-dlp로 자막 다운 또는 ego-lite에서 유튜브 요약된 내용", "c:\winpython\에 cpu, gpu 환경 이용 가능, 또는 상위 관련 프로젝트에서 작성 yt-dlp 이동 파이썬 스크립트 가능". 확인 결과(2026-11-01) yt-dlp(2026.08.19)와 youtube-kit은 cpu 환경에만 있다. youtube-kit은 스스로 트랙을 고르지 않는다. 영상 파일 제외는 루트 INTENT "영상은 자막·요약 같은 텍스트로만 다룬다"이다.

**배제한 대안**

- **항상 자막 + 요약 둘 다** — 사용자가 "요청할 때 고름"을 골랐다. 배제.
- **gpu 환경** — yt-dlp가 설치되어 있지 않다. 배제.
- **yt-dlp 직접 호출** — 같은 기능을 하는 youtube-kit이 이미 있다. 배제.

## D-16. 유튜브 원본은 영상마다 youtube-<영상ID>/ 폴더 하나에 둔다

**선택**

```text
inbox/youtube-<영상ID>/
  <영상ID>.meta.json             youtube-kit info 결과(제목·채널·URL)
  <영상ID>.<종류>.<키>.srt        자막 (고른 경우, youtube-kit 파일 이름 그대로)
  summary.md                     YouTube 요약 (고른 경우), 맨 위에 영상 URL과 가져온 날짜
```

`meta.json`은 고른 것과 상관없이 항상 둔다. youtube-kit이 저장한 파일은 이름·내용을 바꾸지 않는다.

**근거**

사용자 답 "영상마다 폴더". youtube-kit README의 파일 규칙(`<id>.meta.json`, `<id>.<종류>.<유튜브 키>.<형식>`). youtube-kit "받은 파일은 변환하지 않고 그대로 저장한다", D-3 "원본은 고치지 않는다"와 맞는다.

**배제한 대안**

- **영상마다 md 파일 하나** — 받은 파일을 변환하게 된다. 사용자가 고르지 않았다. 배제.

## D-17. frontmatter sources는 문자열 목록으로, URL 뒤에 확인 날짜를 괄호로 붙인다

**선택**

```yaml
sources:
  - raw/math/fft-notes/고속푸리에변환.md
  - https://en.wikipedia.org/wiki/Fast_Fourier_transform (2026-11-01)
```

`raw/` 경로는 그대로, URL은 뒤에 ` (YYYY-MM-DD)`를 붙인다. 유튜브 원본은 `raw/` 폴더 경로를 적는다. 사람과 에이전트가 직접 겪은 일을 페이지에 적을 때는 그 일을 기록한 저장소 안 문서(예: `specs/v0.1/PROGRESS.md`)의 경로를 적는다(2026-11-01 사용자 지시로 추가).

**근거**

사용자 답 "문자열 목록". 저장소 안 기록 문서 허용은 Phase 4에서 사용자 답 "D-17 넓히기"(2026-11-01).

**배제한 대안**

- **항목마다 필드(raw/url/checked)** — 길어진다. 사용자가 고르지 않았다. 배제.

## D-20. 첫 분야는 apps와 dev 두 개로 한다

**선택**

| 분야 | 범위 |
|---|---|
| `apps` | 만드는 앱 자체: 데스크탑·GUI 앱, 동영상 플레이어, 에디터, 그 앱의 요구사항·스택 결정·구조 |
| `dev` | 개발 툴, AI(에이전트·스킬·LLM 활용 포함), 소프트웨어, 하드웨어 |

지금 inbox 원본은 이렇게 나눈다.

- `apps`: `rust-gui/`, `rust-video-player/`, `rust-video-player-native/`, `zed-like-editor/`
- `dev`: `herdr/`, `ego-lite-guide/`, `ssh-tailscale-remote-terminal-guide/`, `youtube-pXTD2DJBlDo/`

폴더는 D-1대로 그 분야의 첫 페이지를 저장할 때 만든다. 두 분야에 맞지 않는 원본이 오면 새 분야를 사람에게 묻는다.

**근거**

사용자 지시 "우선적으로 앱 / 딥러닝 / 개발 / 소프트웨어 등을 먼저 다루고 있습니다", "먼저 apps, dev (개발 툴, AI, 소프트웨어, 하드웨어) 2개로만 해 주세요" (2026-11-01).

**배제한 대안**

- **ai-agents·rust·dev-tools 3개, ai-agents·desktop-apps·dev-tools 3개, ai-agents·dev 2개** — leader가 제안했으나 사용자가 고르지 않았다. 배제.
- **apps·deep-learning·dev·software 4개** — 사용자가 "먼저 2개로만"이라고 했다. deep-learning·software는 문서가 생길 때 다시 묻는다. 배제.
